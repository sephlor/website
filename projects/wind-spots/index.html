🪁 Wind Spots

Work in progress

Try it out:

  • In the chat →
  • — add it to your own agent as a custom connector.

A wind-forecast tool for wind sports that grounds an LLM's answer in real data instead of guesses. It resolves the folk names kiters and sailors actually use — "3rd Ave", "Racetrack", "Crissy" — to the launch-accurate coordinates where the forecast matters, then returns structured conditions the model can only report, not invent.

It runs as a Model Context Protocol server. Add it once as a custom connector and the model stops searching the web for wind.

Why bother

Ask Claude or ChatGPT what the wind is doing at a spot right now and you get an answer that looks confident and isn't much use.

  1. It's slow. Thirty seconds or more of searching, opening pages, hitting paywalls and thinking before anything comes back.
  2. It answers a different question. A pretty weather card showing the temperature and a week of sun icons, then three paragraphs of prose. I asked about the wind.
  3. It gets the place wrong. Ask about Richmond and you may get the middle of town rather than the marina or the beach. Use a local spot name and it can miss the intent entirely.
  4. Even when the spot is right, the numbers often aren't — and there's no way to check them. The model is summarising whatever pages it happened to land on, at whatever resolution those pages publish.

What the tool does

  • Resolves the name first. Entity matching against a gazetteer of spots and aliases — exact name, then alias, then a live geocoder for anything it hasn't learned yet. Curated coordinates are launch and riding points placed by hand, not the geocoder's idea of the town. When several places share a name, a rough location from the model puts the nearest one first.
  • Calls a real weather API. Current conditions plus an hourly curve from Open-Meteo.
  • Returns structured data, not prose. Speed, gusts, direction, temperature. The model writes the sentence; it doesn't make up the number.
  • Several spots in one call. "Crissy or Alameda today?" is a single round trip, back in a second or two — quick enough to keep asking, and to pick before you drive.

What the model does

  • It's nicer to talk to. When a trustworthy answer comes back quickly, you keep going — "what about Alameda?", "and later?", "so where should I drive?" — and it stays a conversation.
  • Understands what you mean. You ask the way you would ask a friend: "is OB working?", "A4 after work?", "3rd Ave this weekend?". The model works out the spot, the hours and roughly where you are, and hands those to the tool in your own words.
  • Corrects itself or clarifies. Every forecast is labelled with the spot it resolved to, so a bad match is visible instead of silent. When a name could be several places, the model asks which one. When the tool lands on the wrong one, it notices and tries again.

Two sets of evals run offline, before and after every change.

  • The resolver on its own. A hand-written set of queries (typos, homonyms, non-spots, places outside the gazetteer) is scored against a saved baseline, so a change shows exactly which rows moved. About 98% pass today.
  • The whole agent. A model is given a rider's question and the tool, and a program checks the run: the right spot, the right hours, and only numbers the tool returned. In a recent run about five in six came through clean.
  • Real questions feed back in. Conversations on the chat page are logged in the same format as eval runs, and any exchange can be turned into a new eval question.

How it runs

  • Deployed, not just a script. Docker Compose on a VPS behind Caddy for TLS.
  • Kept inside the free tier. Outbound Open-Meteo calls are capped per day, so a busy day can't run past the quota.

What's coming next: increased coverage, better ranking, improvements driven by demand, and more!
